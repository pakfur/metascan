# CLAUDE.md — Metascan

## Project Overview

Metascan is an AI-generated media browser with metadata extraction, similarity search, and AI upscaling. It uses a **client-server architecture**: a Python/FastAPI backend handles scanning, database, AI processing, and file serving, while a Vue 3 SPA provides the web UI.

## Quick Reference

```bash
# Run the app (two terminals)
source venv/bin/activate && python run_server.py   # Backend: http://localhost:8700
cd frontend && npm run dev                          # Frontend: http://localhost:5173

# Quality checks (must pass before committing)
make quality test     # flake8 + black --check + mypy + pytest

# Frontend only
cd frontend && npm run build    # Type-check + production build
```

## Key Technical Decisions

- **No UI framework in Python code.** The legacy PyQt6 desktop UI (`metascan/ui/`, `main.py`, `run.bat`, `build_app.py`, `metascan.spec`) was removed; the web stack (Vue 3 + FastAPI) is the only UI. Backend Python must never import `PyQt6` or `qt_material`.
- **Database access is synchronous** — wrapped with `asyncio.to_thread()` in the service layer for FastAPI compatibility. The threading.Lock in DatabaseManager handles concurrency.
- **Background workers use subprocesses** (not threads) for embedding generation and upscaling, communicating via JSON files. This avoids GIL issues with heavy AI workloads.
- **Two separate CLIP subprocesses.** `embedding_worker.py` is one-shot batch (computes embeddings + CLIP tags for unembedded files and exits). `inference_worker.py` is long-running (NDJSON stdio — answers `encode_text` / `encode_image` / `encode_video` for live searches). Both load their own CLIP model; do not share state. The live path is supervised by `InferenceClient` (asyncio) installed on the FastAPI app via `lifespan`.
- **Inference worker stderr is drained** line-by-line into the server logger by `InferenceClient._stderr_loop`. Do not switch to `stderr=PIPE` without a drainer — the pipe buffer fills during model load and the worker hangs silently.
- **FastAPI uses `lifespan`** (not the deprecated `@app.on_event`). Its first step opens the database (`_open_database`): a `MigrationError` (e.g. the v6 backup refused for disk space) is logged at CRITICAL and re-raised, so the server refuses to start rather than serve a half-migrated library; the next start retries. The lifespan constructs the `InferenceClient` singleton, installs it into `backend.api.similarity` via `set_inference_client`, injects `HF_TOKEN` env from `config.models.huggingface_token`, and optionally preloads CLIP for the current model if `config.models.preload_at_startup` includes `clip-<key>`.
- **Similarity endpoints call `client.ensure_started`** before `encode_*` so a search request arriving before preload still triggers a spawn rather than blocking on a ready event that will never fire.
- **Dim-mismatch guard.** Before FAISS search, `_assert_dim_matches` returns HTTP 409 `{code:"dim_mismatch", index_dim, model_dim, ...}` when the current CLIP model's embedding dim differs from the on-disk index. The frontend's `ApiError` in `client.ts` preserves `detail` so the UI can render an actionable "Rebuild index" banner.
- **HuggingFace HEAD probe suppression.** `embedding_manager._check_model_needs_download` is authoritative; when weights are cached, the loader sets `HF_HUB_OFFLINE=1` around `open_clip.create_model_and_transforms` to skip the etag revalidation.
- **Core modules use callbacks** for event dispatch: `on_progress`, `on_complete`, `on_error`, `on_status`, `on_task_added`, etc.
- **WebSocket is multiplexed** — a single `/ws` connection carries all channels (`scan`, `upscale`, `embedding`, `watcher`, `models`, `folders`, `comfy`, `storyboard`, `i2v`, `t2i`, `categories`, `taste`, `training`) with JSON envelope `{channel, event, data}`. The `training` channel (writer-LoRA training, see `.claude/rules/writer-training.md`) broadcasts `adapters_changed {}` on every writer-adapter rename/delete/status change/promotion (refetch `GET /api/writers/adapters`); `gate_changed {}` after every base/converter download or delete; `run_started {run_id, adapter_id, name, scope, resumed}`, `run_progress {run_id, adapter_id, stage, step, total_steps, stage_step, stage_total, loss, holdout_agreement, base_agreement, eta_s, last_checkpoint_step, last_checkpoint_at, updated_at}`, `run_paused {run_id, adapter_id, step, total_steps}`, `run_completed {run_id, adapter_id}`, `run_failed {run_id, adapter_id, error}`, `run_cancelled {run_id, adapter_id}`; `briefs_progress {done, total}`, `briefs_done`, `briefs_cancelled`, `briefs_error {code}` (hindsight briefs job); and the scorecard events `scorecard_started {scorecard_id, adapter_id, total, todo, resumed, target_model}`, `scorecard_progress {adapter_id, scorecard_id, phase, done, total}`, `scorecard_complete {…, status, done, total, missing}`, `scorecard_failed {adapter_id, scorecard_id, code, error}`, `scorecard_cancelled`, `scorecard_judged {adapter_id}`. A client that missed events (WS gap, server restart) refetches `GET /api/writers/training` on reconnect. The `models` channel broadcasts `inference_status`, `inference_progress`, `download_progress`, `download_complete`, `download_error`. The `folders` channel broadcasts `folder_created` / `folder_updated` / `folder_deleted` / `folder_items_changed` for cross-tab sync. The `taste` channel broadcasts `training_started {}`, `training_complete {model_id, holdout_auc, n_pos, n_neg}`, `training_failed {error}` and `scores_updated {model_id}` (after every successful train or rescore) from `TasteService`, and `reembed_progress {reembed}` from the tombstone re-embedder (`{running, done, total}` while a pass is unfinished, null when it ends). The `storyboard` channel broadcasts `synthesis_progress` (`{storyboard_id, panel_id, beat_id, done, total, prompt_source}`), `synthesis_complete` (`{storyboard_id, synthesized, fallback, skipped_locked}`), `synthesis_error` (`{storyboard_id, error}`), and `beat_images_changed` (`{storyboard_id, panel_id, beat_id, files}`) from `StoryboardRunner`'s own `on_event` callback — the `folder_created` / `folder_items_changed` events it also emits go out on the `folders` channel, not `storyboard`. `POST /api/storyboard/{id}/synthesize` is 202 fire-and-forget (`asyncio.create_task`); `synthesis_complete`/`synthesis_error` are the only signal a client gets that the background run actually finished or died — `StoryboardRunner.synthesize` wraps the real work and always emits exactly one of the two, re-raising after `synthesis_error` so a direct (non-route) caller still sees the exception.
- The `categories` channel broadcasts `categories_changed` (`{}`) on every category create / rename / delete / membership change and when a grade adds a sticky category link; clients refetch `/api/categories`, and when a T2I/I2V ingest tags its output (runners emit it through their own `on_event`, channel `categories`).
- **★ favorite and the ✓ pass / ✗ fail grade are independent** (spec `docs/superpowers/specs/2026-10-24-pass-fail-grades-design.md`). `media.is_favorite` (★) is view only and never a training input; `media_judgments.grade` (`'pass'` / `'fail'` / NULL) is the only training signal for every consumer; neither marker sets or clears the other, and viewing (`seen_at`) is never a label. `set_grade`: the same grade again refreshes `confirmed_at` only; a change or clear logs `grade_pass` / `grade_fail` / `grade_clear` (with `score_shown`), clears the reasons and sets `judged_at = confirmed_at`. Any non-null grade links the sticky category (`sticky_category_id`), the same grade again included; a clear never links one. `set_favorite` / `set_favorite_state` are ★ only (`favorite` / `unfavorite` events). A reason needs a grade (409 `no_grade`); `mark_seen` logs `seen` once and never reconfirms. `PATCH /api/judgments/{path}` takes exactly one of `{grade, score_shown?, sticky_category_id?}`, `{favorite}`, `{reason, on, score_shown?}` (else 422, the old `verdict` field included); only a grade runs `notify_scorecard_judgment`. The legacy `PATCH /api/media/{path}` `{is_favorite}` is ★ only; its summary-row answer leaves `grade` out when the read fails, so the grid keeps its badge. **Never reuse `pass` / `passed` / `unpass` / `verdict` for the new ✓**: in every pre-v6 column, event and snapshot they mean *reject*; the old events are read only by the score_shown legacy mapping (`taste_labels.LEGACY_GRADE_EVENTS`). `tests/test_grades_guard.py` fails on backend code that names a `passed` column, key or attribute outside its allow-list (`PASSED_ALLOWED`: the v6 migration `_migrate_to_v6`, the old-SQLite tombstone placeholder `_legacy_tombstone_fill`, and the legacy snapshot translation `upgrade_legacy_snapshot` / `_valid_judgment`), on frontend code that reads a `passed` field (`test_the_frontend_reads_no_passed_field`), and on code that reads an old event as ✓.
- **Judgments and tombstones.** Taste judgments live in `media_judgments` plus the append-only `judgment_events` log. Every per-item media-row delete writes a `media_tombstones` row first — choke points: `delete_media`, `delete_media_batch`, `_purge_media_rows`; T2I/I2V deletes purge before dropping their lineage row. A tombstone copies `grade`, reasons, categories, `judged_at` / timestamps and the T2I/I2V lineage (`scorecard_id` from it, indexed: the scorecard finds deleted images by it), plus what a deleted graded image still teaches: its hindsight brief and model (`hindsight_briefs` cascades, so it is copied first), a ✓ library image's metadata `prompt` and `model_name` (a JSON list of its model names), and `thumb_path`, an archived thumbnail (`metascan/core/training_archive.py`: graded **images** only, made from the live file into `<data dir>/archive/thumbs/<uuid>.jpg`, longest side ≤ `ARCHIVE_MAX_PX = 512`, JPEG q85, stored relative to the data dir; a failed archive is logged and never blocks the delete), and `embedded_model`, the evidence that a FAISS row read by its path is its own (Tombstone vectors bullet). Delete order on every path: archive → trash → DB delete (`delete_keeping_signal`; a failed trash discards the archive and keeps the row). T2I / I2V deletes trash only `db.purgeable_paths` (`delete_generated`: a file a storyboard still uses is released, never trashed); storyboard purges archive the graded beat images they will delete first (`purge_keeping_signal` + `db.purge_image_candidates`) and still trash after the rows; the stale-file cleanup keeps everything but the thumbnail, and so does a completed full clean for a path its rescan did not find (from the snapshot, next bullet; its `embedded_model` is NULL: the truncate took the record). Routes: `/api/judgments` and `/api/categories`; category sources `generation` / `sticky` are server-internal and rejected (422) from the API.
- **Full clean & rescan keeps ratings, and what a vanished image teaches.** `truncate_all_data` cascades `media_judgments` / `media_categories` / `hindsight_briefs` away (the media data blob and `indices` rows a library prompt is read from go with the media rows) and writes no tombstones, so `_run_scan` takes `db.export_taste_state()` first (version 3, `TASTE_SNAPSHOT_VERSION`: each judgment row carries its `grade`; `favorites` is the ★ list; `briefs` holds every `hindsight_briefs` row `{file_path, brief, model, created_at}`; `library_prompts` each ✓ library image's `{file_path, prompt, model_name}` exactly as `_library_prompt` gives a delete's tombstone — `model_name` the sorted JSON list text; `_keeps_library_prompt`, the rule `_write_tombstones` uses, picks the images, and one with neither is left out) and writes it to `<db dir>/taste_snapshot_before_full_clean.json` (the clean aborts before deleting anything if either fails). That file is **pending state**, owned by `backend/services/taste_snapshot.py`, and is deleted only when nothing is left in it. `db.restore_taste_state(snapshot, tombstone_missing)` takes version 3 only and puts rows, links and briefs back verbatim for paths whose media row exists again — original timestamps (decay clocks must not restart; a brief keeps its model and `created_at`), ★ by raw UPDATE, **no** new `judgment_events` — but never overwrites newer data: a live row with a grade, a reason or a `judged_at` keeps its row, a seen-only row is filled; the snapshot's ★ comes back on its own (even beside a newer grade) and a restore never clears ★; category links and briefs are `ON CONFLICT DO NOTHING` (a path briefed again after it re-appeared keeps that brief). A snapshot path is any path with an entry. It returns the counts plus `remaining` (the snapshot narrowed to unrestored paths, their briefs and library prompts included, still version 3). A version-2 file (grades, neither list) reads as version 3 with no briefs and no prompts. A version-less file was written before grades: `upgrade_legacy_snapshot` translates its rows on load exactly as v6 maps live ratings (`passed = 1` → ✗, a favorite → ★ + ✓, a favorite with no row gets a ✓ row), so it restores and is never quarantined for its shape. A row that already carries `grade` (the interim export of the grades work, still version-less) is taken as stored, row by row, and a file with any such row makes no rows for bare favorites (there ★ is not a grade); any other version is quarantined. A **completed** full clean restores what came back, tombstones the rest (one tombstone per path, `_tombstone_from_snapshot`: the snapshot's brief and brief model, a ✓ library image's prompt and model names, the surviving T2I / I2V lineage — for a path a delete would tombstone, the row the delete writes, minus the thumbnail and the FAISS evidence (`embedded_model` / `embedded_at` NULL, no vector: Tombstone vectors bullet): the rescan did not find the file, so there is none to archive and a ✓ image left without a brief can never get one; a ★-only or brief-only path, which a delete never tombstones, gets one too, with no grade) and deletes the file. A **cancelled or failed** one (including a cancel that lands during the last directory) restores what came back so far, writes **no** tombstones and rewrites the file with only the unrestored entries (briefs and prompts included). A **shutdown** mid-scan (`CancelledError`) touches nothing — no code path may delete the file on `CancelledError`. `apply_pending_taste_snapshot(db, data_dir)` (restore-what-reappeared, never tombstones, rewrite/delete the file) runs from the `lifespan` at startup (after migrations) and at the end of every scan. A new full clean first applies the pending file, then merges its leftovers (`merge_pending_into_snapshot`, every list) into the new snapshot, so a later completed full clean tombstones them like any other missing path. The file is written with fsync of the data and the directory before the truncate. A pending file that fails to parse (it is read as bytes and decoded in the `try` that quarantines: not UTF-8, not JSON, or nested deeper than the parser goes), has the wrong shape, version or value types (a brief or library-prompt field that is not text SQLite can store — UTF-8: a JSON `\udc80` escape reads as a lone surrogate, which binding would reject halfway through the restore —, a `model_name` that is not the JSON text of a list of names), or that `restore_taste_state` rejects (TypeError / ValueError / KeyError / IntegrityError / ProgrammingError, logged by the error's type only: its text can quote the data) is renamed to `<name>.corrupt-<timestamp>-<pid>-<n>` and logged — never retried, never fatal. The readers name each version they take (`_READABLE_VERSIONS = (2, 3)`, `== 2` for the version-2 shape; `upgrade_legacy_snapshot` raises ValueError for a versioned file it has no step for), so a version bump must add how it reads version 3 rather than read it as version 2 and drop its briefs. A build older than version 3 sets a version-3 pending file aside the same way (unknown version), and nothing is lost: after upgrading, while no pending file exists, rename that `.corrupt-*` file back to `taste_snapshot_before_full_clean.json` and the next start or scan applies it. Briefs and prompts are training text: the snapshot code never logs them (counts only; `tests/test_taste_snapshot_briefs.py`). A pending file that exists but can't be read (locked, permissions) or can't be quarantined raises `PendingSnapshotUnreadable`: startup / end-of-scan apply log it and leave the file, and a full clean **aborts before truncating** (it would otherwise overwrite the file). If deleting a consumed file fails it is retried once and then overwritten with an empty snapshot, so handled entries are never re-restored or re-tombstoned. Never restore via `set_grade` / `set_favorite` — they log events and reset the timestamps. `judgment_events` and `categories` have no FK to `media` and must stay untouched by the truncate. **The T2I / I2V lineage prune pauses until a full clean is finished:** `list_t2i_images` / `list_i2v_videos` still list only rows whose media row exists, but delete none. The rescan re-adds media rows one by one, so a single listing mid-rescan (the T2I dialog opening, a WebSocket reconnect) used to wipe every lineage row — prompts, drafts, writer ids, variant groups, scorecard ids — and the completed full clean reads a vanished item's lineage from those rows when it tombstones it. A paused `list_t2i_images` is ONE inner-JOIN query with the limit and the cursor (its refill loop walked the dangling rows a round trip at a time under the DB lock: 1.25 s per listing for 50k of them). The guard is `db.set_lineage_prune_guard(taste_snapshot.lineage_prune_guard(<db dir>))`, installed in `lifespan` (metascan/core never imports backend; if it can't be built the lifespan installs `lambda: True` — prune nothing — instead), and is true while any of three holds: `full_clean_running()` (`_run_scan` wraps the whole full-clean run and drops it however the run ends); the pending file exists (a library with no ratings still writes one, with empty lists); or the **marker** `<db dir>/full_clean_incomplete` exists. A full clean writes the marker FIRST, before it applies or writes the pending file (`write_full_clean_marker`: data and directory fsynced); when it can't be written the clean stops with nothing written, since a snapshot left behind could later put back a ★ or category the user removed. **Generated output comes back by re-ingest:** T2I / I2V files enter the library through ComfyClient's `Scanner.ingest_file`, under the ComfyUI output root, usually outside every scan folder, so the folder walk never re-adds them. After the walk (not after a cancel, and with the cancel checked between files), while a full clean is unfinished — this run is one, or the marker exists — the scan route re-ingests every `db.generated_paths_without_media()` path whose file is still on disk (`_reingest_generated_files`), before the taste restore: their ratings come back and their lineage stays attached. Each path is `_generated_file_state`: present (re-ingested), **gone** (its folder is there, the file is not: vanished, tombstoned with its lineage like any other) or **unreachable** (its folder is missing or can't be read — an unmounted `t2i.output_root` / `i2v.output_root` — so it may well still exist). The step reports whether every generated file still on disk came back: an unreachable path, a file whose ingest raised or returned None, or a candidate query that raised makes the run **unfinished** — restore with `completed=False` (no tombstones, the ratings stay pending) and the marker stays — exactly like the missing-folder rule; a later scan that brings them back finishes it. The log carries counts and exception types only, never a path. An output folder deleted for good therefore keeps the clean unfinished until the marker (and, for its ratings, the pending file) is deleted by hand. Only the scan route's completion removes the marker (`clear_full_clean_marker`): a scan — full clean or ordinary — that walked at least one and every configured folder (none missing) to the end and brought every generated file still on disk back, with no cancel (one in the last folder included) and no error. Then every file still on disk in a configured folder, and every T2I / I2V output still on disk, has its media row again. Cancel, failure, shutdown and restart keep it, and the startup / end-of-scan apply never touches it: the pending file only lists rated paths and can be gone (or empty from the start) long before the rescan reaches the unrated files. A failed removal is logged at ERROR and keeps the pause. **To resume pruning by hand, delete `full_clean_incomplete` from the data dir** (`data/` in a source checkout, `~/.metascan/data/` bundled; the marker's own text says how too) — no restart needed, but it resumes only when no full clean is running and no pending file holds the pause. A pause held by the pending file ends, most often, once its last entries come back: the apply at startup and at the end of every scan consumes the file when nothing is left in it. Otherwise it ends when a later full clean completes (it tombstones the leftovers and deletes the file); deleting the pending file by hand ends it too, but drops those ratings — they are never tombstoned. The guard is read once per listing under the DB lock, so a truncate cannot land between the read and the delete; a guard that raises counts as paused (one WARNING per `PRUNE_GUARD_WARN_INTERVAL_S` = 1 h, DEBUG in between). With none of the three, a deleted file's orphan row is pruned as before; `delete_t2i_image` / `delete_i2v_video` never pause.
- **Tombstone vectors, one per CLIP model** (`tombstone_vectors(tombstone_id, model_key, embedding, created_at)`; v6 copied the legacy `media_tombstones.embedding` / `embedding_model` columns there, and nothing reads or writes them since). Readers (taste labels, ✓ diversity) take only the FAISS index's model's vector, and **never read the index by a tombstone's old path** (another file may live there now). **A path's FAISS row holds the vector of the last file embedded there:** `FaissIndexManager.add` / `add_batch` overwrite the row of a path already in the index (in place for a flat index, else by rebuilding it), so a "Rebuild all", a full rescan (which resets `has_embedding`) and a new file on a deleted file's path all refresh it; a file edited in place outside Metascan is picked up only by a rescan that re-ingests it. A deleted file's row stays in the on-disk index until another file is embedded at its path or the CLIP model changes (a rebuild skips missing files). So the index is read by a tombstone's path only **with evidence** that the row is its own file's, kept in three `media_tombstones` columns: `embedded_model` and `embedded_at`, written at deletion by `_write_tombstones` from the file's `media_hashes` row (still there before the cascade) — its `clip_model` and `embedding_updated_at` (the mark's time) when `has_embedding = 1`, `''` / NULL when it was never embedded (never read by path), NULL / NULL when nothing is known: a tombstone written before the columns, the ones `restore_taste_state` writes after a full clean (the truncate took the record) and a file whose mark has no time (made before the fix: v7) — and `path_rewritten`, set to 1 on **every** tombstone of a path whenever the embedding worker appends or overwrites that path's row (any model, any index, a fresh one after a CLIP switch included) by `db.mark_tombstone_paths_rewritten(batch_paths)` (POSIX paths, `idx_media_tombstones_path`) **before** each `faiss_mgr.save()` — every 100 files and at the end; an `sqlite3.OperationalError` (a lock) is retried after `STAMP_RETRY_DELAYS_S` (0.5 / 1 / 2 s), any other error is not, and a stamp that still fails saves nothing (periodic: the batch carries over; final: the run fails and its files are embedded again). The evidence also needs the **index read to be loaded after the mark**: `FaissIndexManager.loaded_at` (UTC epoch, taken before `load()` reads the files; None for an index not loaded from disk) ≥ `embedded_at` + `MARK_RESOLUTION_S` (1 s: `CURRENT_TIMESTAMP` drops the fraction), `_loaded_after_mark`, because the server's in-memory index is replaced only after a run completes (never after a failed one) and so can lag the disk; the reload after a run (`similarity._rebuild_faiss_manager`) first waits for the next whole second (`_wait_for_the_next_second`, at most 1 s, off the loop) so the run's last marks count for the index it loads. The worker marks a file only **after** the save that holds its row succeeded (a failed save leaves the batch unmarked until a later save works; a failed final save still ends the run `complete`, with `errors_count` / `last_error` saying so). A skipped read keeps its evidence, so the backfill on a later load can still fill it. The embedding queue keeps indexing (a new build is refused) until the worker **process has exited**, even after it wrote its last status — a cancelled worker still stamps, saves and marks its batch — so the index has one writer and the reload sees the final save; one that has not exited `FINAL_EXIT_WARN_S` (60 s) after its last status is logged at WARNING once a minute. The worker's stdout goes to DEVNULL and its stderr is drained line by line on a daemon thread into the server log (`EmbeddingQueue._drain_stderr`; the last `STDERR_TAIL_LINES` = 200 lines kept for the error message): a pipe nobody reads holds 64 KB and then blocks the worker for good (a full disk makes it log an error per file, and logging's own error dumps go to stderr). The worker logs its errors with their tracebacks (`logger.exception`) and its warnings (`logging.captureWarnings`) to its own log file; never send its stderr to a file the server opens (`tests/test_log_files.py`). Never hand a replaced row to a tombstone (the worker cannot tell whose it was) and, when unsure, store no vector. Three writers: at deletion, `db.set_embedding_lookup(faiss_embedding_lookup)` (installed in `lifespan`; it returns `(vector, model_key, loaded_at)`) reads only the already-loaded in-memory index — it runs under the DB lock, so it must never load from disk — and only for a file whose `embedded_model` is that index's model and whose `embedded_at` predates its `loaded_at`; when `_get_faiss_manager` next loads an index, `_start_tombstone_backfill` runs `judgments_service.backfill_tombstone_embeddings` on a daemon thread — `db.tombstones_for_vector_backfill(model_key, loaded_at)` lists only tombstones with `path_rewritten = 0` and either `embedded_model` = the index's model marked before the load (no vector for it yet) or `embedded_model` NULL under the old guards (no vector for any model, no archived thumbnail, a path no live media row or other tombstone holds), FAISS reads happen **outside** the DB lock, then `db.add_tombstone_vectors` (INSERT OR IGNORE); and `backend/services/tombstone_reembed.py::TombstoneReembedder` encodes graded tombstones' archived thumbnails through the live inference worker's `encode_image` for the index's model, only while the configured CLIP model agrees. The re-embedder starts CLIP itself and yields to `reembed_blocked` (GPU lock, a T2I batch or ComfyUI job, an index build), checked before CLIP starts and between images; it is deliberately not a training `gpu_busy` reason (training wins), and its retry and CLIP-error rules are in its module docstring. The lifespan notifies it at startup and after every embedding run (`_after_embedding_run`) and closes it first at shutdown, before training lets go of the GPU lock; a pass that added vectors calls `TasteService.mark_due("reembed")`; progress is status `reembed` and the taste `reembed_progress` event. Rows the code before the overwrite left stale are reset by v7 (user_version list).
- **Writer-LoRA training is a subprocess behind a GPU lock.** `TrainingManager` (`backend/services/training_manager.py`) spawns `python -m metascan.workers.writer_train_worker task.json` (the training interpreter: `models.writer_train_python`, default the server's `sys.executable`); the worker talks only through JSON files in `data/training/runs/<run_id>/` (`task.json`, `progress.json`, `result.json`, `control/pause.signal` / `cancel.signal`, exit codes 0 ok / 1 error / 3 paused / 4 cancelled) and only the lazily imported backend touches torch/TRL/PEFT — the FastAPI process never imports them. Examples (preference/edit/hindsight) are never logged, only counted; the window's Preview is the one place text leaves `writer_dataset`. While a run is active `metascan.core.gpu_guard.gpu_reserved()` is true: every GPU consumer route declares `GPU_FREE` (409 `gpu_busy_training`, "GPU busy: training") and the core clients (`VlmClient.start`, `InferenceClient.start`, `ComfyClient.submit`, index build, upscale queue) refuse too; a new consumer of the GPU must do both. Start takes the lock first, refuses on `gpu_busy` reasons, then unloads the VLMs and CLIP. The `writer_training` gate needs CUDA with >= 32 GB VRAM, the training deps (probed in a background subprocess, cached), the TRL pin (`trl>=0.25,<0.26`), base weights and the converter. Details and invariants: `.claude/rules/writer-training.md`. User guide: `docs/writer-training.md`.
- **Adapters are served by the writer llama-server (`--lora`).** One `llama-server` per writer carries every ready/untested adapter (`--lora <gguf>` each, `--lora-init-without-apply`), selected per request by `lora: [{id, scale}]`; writer ids are `adapter:<id>` and adapter names never reuse a number. Rules in `.claude/rules/vlm-llama.md`.
- **Taste scorer.** A per-user "would I pass this?" score per image (the chance you'd grade it ✓), learnt from grades only. Pieces: `metascan/core/taste_labels.py` (pure labels: ✓ → 1, ✗ → 0, no grade → excluded — ★, views and categories alone never count; weight `0.5 ** (age_days / half_life_days)` from `COALESCE(confirmed_at, judged_at)`, ×0.5 when the grade's newest `grade_*` event carried `score_shown` — for a grade v6 made from an old verdict (no grade event), the last old `favorite` (✓) / `pass` (✗) event at or before `judged_at`, `LEGACY_GRADE_EVENTS`; later ★ events never count; the viewer sends the score on screen with each grade; **review mode (`R`) is the queue of scored images with no grade, nearest 0.5 first, and runs no seen dwell timer**; within-T2I-batch ✓ / ✗ pairs; a deleted image is labelled by its newest *graded* tombstone, a graded live row wins; every label row says `tombstone` (required) and the worker reads the index by path only for live rows; needs 20 ✓ and 20 ✗), `metascan/workers/taste_worker.py` (one-shot subprocess, JSON task/result files, numpy + faiss — the FastAPI process never fits), `metascan/core/taste_runner.py` (snapshots labels, spawns the worker, records `taste_models` / `taste_scores`), `backend/services/taste_service.py` + `backend/api/taste.py` (`/api/taste/status|train|scores|review-queue`). **Images only** — videos are never labels or scored. `LABELS_VERSION = 2` (runner and worker, tested equal; `taste_models.labels_version`): an active model trained on the pre-grades labels is due at once and keeps serving its scores until the retrain lands (status `labels_outdated`). A model is **stale** when the FAISS index's `model_key`/dim differ from the model's: no scores served, status `stale: true`, auto-retrain treats it as due. `labels_as_of` is the snapshot time, so ratings made while training count toward the next run. Auto-retrain (`TasteService.retrain_loop`, every `RETRAIN_CHECK_S = 30` s): when `config.taste.auto_retrain`, the embedding queue is **not** indexing (a rebuild rewrites the index every 100 files), and (no model yet, stale, outdated labels, marked due by `mark_due(reason)` (the re-embedder), ≥ `RETRAIN_MIN_EVENTS = 25` events since `labels_as_of` of `TRAINING_EVENT_KINDS` — grade, reason and category events on images, never ★, seen or the old events — or — after an embedding run — the active model was trained with more than `MAX_NO_VECTOR_SHARE = 10%` of its labeled rows lacking a vector, `taste_models.n_no_vector`) and no such event for `RETRAIN_IDLE_S = 120` s and labels suffice; the **worker** re-checks the 20/20 minimum on rows that actually have a vector and returns `not_enough_data` with `reason: "vectors"` (no failed row, no model; status `missing` + `missing_reason: "vectors"` until the next embedding run), so a partial index after a CLIP switch can never activate a near-empty model; status `new_events` is null while there is no model; a failed auto run is not retried until its inputs change (new events, active model, or the index fingerprint `model_key`/dim/`index_meta.json` mtime) or an embedding run completes. `missing` comes from the slim `taste_label_counts_raw` + `count_labels` (same rules as `build_label_set`), never the full training snapshot. At most one training task (`POST /train` → 202, or 409 `already_training` / `not_enough_data`); every runner exception becomes `last_error` + `training_failed`. A rescore requested while a train or rescore is running is coalesced into one follow-up run. Each completed embedding run triggers a rescore and then notifies the tombstone re-embedder via `similarity.set_embedding_complete_hook` (`_after_embedding_run`; fires on the poller's worker thread → `call_soon_threadsafe`); fresh T2I images reach that path through `AutoIndexScheduler` (see `.claude/rules/t2i.md`). `check_stale` (every loop tick and after a rescore that returned nothing) broadcasts `scores_updated {model_id: null}` once when the active model turns stale, so the browser drops its map. `fit` balances the classes (each class's total sample weight equal) so a library of thousands of migrated ✓ vs a few dozen ✗ still centres on 0.5. If writing the scores fails after the model row is recorded, the run returns `rescore_needed` and the service rescores once it ends. Rescore reads `taste_scoring_raw` (paths + categories), never the full training snapshot. Lifespan shutdown closes the re-embedder first, stops the embedding queue and clears the hook before `TasteService.aclose()` cancels the loop and any in-flight train/rescore (the runner kills its worker on cancel). Status also carries `reembed` (`{running, done, total}` or null). Config: `"taste": {"half_life_days": 180, "auto_retrain": true}`. **Writer stats** (`GET /api/taste/writer-stats` → `{window_days, window_starts, windows, diversity, collapse_warning}`, Config → Training "Writers"): `db.writer_window_stats` rows are `{n_graded, n_pass, rate = n_pass / n_graded}`, the pass rate among GRADED generations (★ and views count in neither number) per `(writer_id, writer_model)` (NULL writer → `unknown`; NULL model stays null — typed, fallback, or older rows) per 14-day window by generation `created_at` (UTC, last 6, newest ends today), T2I and I2V separate; deleted generations count via their tombstone `lineage` unless the path is live again (a live row wins, then the newest tombstone); scorecard images (live or tombstoned) are excluded; every `generation_outcomes` row says `tombstone` (required). Every train run's worker also computes ✓ pass diversity (mean pairwise CLIP cosine distance of ✓ T2I generations per window; a deleted one by its `tombstone_vectors` row for the index's model) into `taste_diversity(window_start PK, n, mean_distance, computed_at)`; failures never fail training, and the API serves the newest run's rows with `computed_at`. `taste_labels.collapse_warning`: latest diversity < 0.75 × median of the previous up-to-5 windows **and** pooled T2I pass rate rising **and** the latest window has n ≥ 5 ✓ images with vectors (`COLLAPSE_MIN_PASSES`) — only when the latest diversity window starts within `window_days` of the latest rate window (stale diversity never flags).
- **Tag inverted index tracks source.** `indices.source` is one of `'prompt'` / `'clip'` / `'both'` for tag rows, NULL for other index types. `_generate_indices` emits `(type, key, source)` triples; `_update_indices` preserves CLIP-sourced tags across rescans by downgrading `'both'` → `'clip'` before rewriting prompt rows. Use `db.add_tag_indices(path, tags, source='clip')` from the embedding worker — it upserts with conflict-merge.
- **Folders persist via `/api/folders`.** Two tables: `folders(id, kind ∈ {manual,smart}, name, icon, rules JSON, sort_order, created_at, updated_at)` and `folder_items(folder_id, file_path, added_at)` with `ON DELETE CASCADE` on both sides. The frontend Pinia store (`stores/folders.ts`) does optimistic local updates with API-backed persistence and rolls back on failure. The `folders` WS channel broadcasts every mutation so other tabs stay in sync. A one-shot localStorage → API import runs on first load when the server returns empty; guarded by a localStorage flag.
- **`modified_at` / `created_at` carry two historical shapes.** New rows write an ISO-8601 (or SQL-timestamp) string; rows back-filled from the pre-existing `Media` JSON blob hold a unix-epoch float stringified (e.g. `"1775691760.0"`). The smart-folder "Modified" / "Added" evaluator tries `Number(raw)` first (epoch seconds × 1000) and falls back to `Date.parse`. Both backend and frontend must tolerate either shape.
- **`save_media` uses a true upsert** — `INSERT … ON CONFLICT(file_path) DO UPDATE SET …`, **not** `INSERT OR REPLACE`. The latter is DELETE+INSERT under the hood, which re-fires `created_at`'s `DEFAULT CURRENT_TIMESTAMP` every rescan and collapsed the "Added" smart-folder rule onto a single date. The ON CONFLICT path preserves the original ingest time across rescans. It also never changes an existing row's ★ (`is_favorite = media.is_favorite`; only the ★ paths do — a re-ingest used to clear it silently); a new row takes the caller's value.
- **Covering indexes must include every SELECT column.** `idx_media_summary_added` and `idx_media_summary_modified` back the grid list endpoint and are the reason `/api/media` returns in ~6 ms instead of ~25 s (the `data` JSON blob has 700+ MB of overflow pages on large libraries). When you add a new column to the summary SELECT, extend both indexes. `_init_database` rebuilds any index whose DDL is missing a currently-required column by reading `sqlite_master` (`_ensure_index` for single indexes). `idx_media_judgments_grade (grade, file_path)` covers every "which paths are ✓" read. The grid's `grade` is not a media column: `get_all_media_summaries` reads it with the separate index-only `_SUMMARY_GRADES_SQL` in the same read transaction (a LEFT JOIN probes `media_judgments` per media row: +18–26 % against +6 %), keeping the media read's covering plan.
- **One-shot data migrations are gated on `PRAGMA user_version`.** e.g. `user_version = 1` is the "`created_at` backfilled from `modified_at` on existing rows" migration; `user_version = 2` is the thumbnail-cache wipe for EXIF-orientation handling; `user_version = 3` is the shot/beat model reorganization — drops and recreates `panels`/`beats`/`panel_images→beat_images` (dev data is disposable by decision, no column copying), first unhiding media the old `panel_images` table left hidden and deleting `generation_jobs` rows with a non-NULL `panel_id` so a restart can't re-adopt jobs for panels that no longer exist; `user_version = 4` is the storyboard roster `subject_type` inference — every pre-existing `storyboard_subjects` row is run through `infer_subject_type(name, description)` and rewritten to `location` / `prop` only when the name makes it obvious (everything else stays `character`; deliberately conservative, the user corrects the rest in the UI); `user_version = 5` is the taste-rating seed — every existing `is_favorite = 1` row gets a `media_judgments` row (no reasons, `seen_at` / `judged_at` / `confirmed_at` = migration time) plus one `favorite` `judgment_events` row; `user_version = 6` is the pass / fail grades migration (`_migrate_to_v6`) — a backup first (`backup_before_v6`: `<db file>.pre-v6-<UTC YYYYmmdd-HHMMSS>.bak`, 1.2 × the database size free, skipped when there is nothing to migrate; it holds the database's write lock until the copy is in place and first removes the `.bak.partial` files a start killed mid-backup left — a second start waits, `V6_BACKUP_LOCK_TIMEOUT_S`, rather than remove a backup still being written), then ONE transaction: favorites → ✓ (a rowless favorite gets a row dated now), the old `passed = 1` (a reject) → ✗, the rest ungraded, tombstones likewise, tombstone embeddings into `tombstone_vectors`, tombstone `scorecard_id` from the lineage, then both `passed` columns dropped (SQLite ≥ `DROP_COLUMN_MIN_SQLITE` 3.35.5; older keeps them unread, and a new tombstone fills its NOT NULL copy with 0, `_legacy_tombstone_fill`). The drops run in a SAVEPOINT: a drop SQLite refuses (something in the schema names the column, e.g. a view) is undone and the columns stay unread, with one WARNING, and the upgrade completes. Kept columns stay for good — v6 runs once, so a database upgraded on an old SQLite keeps them after SQLite is updated. No events, no timestamp touched; the counts line is INFO, DEBUG when every count is zero (a new database). Any other failure rolls it all back (still version 5) and raises `MigrationError` (lifespan bullet); once the rollback is confirmed (`_roll_back_v6`: version 5 again) the attempt's backup is deleted, since the database still matches it, so a failure that repeats never piles up copies (an unconfirmed one keeps it and names it); `user_version = 7` (`_migrate_to_v7`) re-embeds the live files the old `FaissIndexManager.add` (which kept a path's first vector) left holding a deleted file's row: every live `media_hashes` row whose path also has a tombstone gets `has_embedding = 0` (an unreadable file's -1 too, so it is retried), and the next incremental build re-embeds and overwrites it. A reused path whose deleted file left no tombstone (no grade, category or lineage) cannot be told apart — its row stays stale until "Rebuild all" — so v7 also clears `embedding_updated_at` on every `has_embedding = 1` row it does not reset: a mark made before the fix is no evidence (such a file's tombstone gets `embedded_model` NULL: the old guards, no capture), and the fixed worker's marks carry a time again. It only resets flags and times (no backup), in one transaction with the version re-read under the write lock; the counts line (never a path) is INFO, DEBUG when both counts are zero; a failure rolls back (still version 6) and raises `MigrationError`. Bump the version when adding new backfills; the gate prevents re-running and silently double-writing on every launch.
- **DELETE endpoints return `{status: "deleted"}` (not 204).** The frontend `request<T>` wrapper in `api/client.ts` calls `res.json()` on every response; 204 No Content would fail the parse. If you need a DELETE with a body, use the `del(path, body)` helper added for `/api/folders/{id}/items`.
- **`pillow_heif` encoder segfaults on some ARM macOS builds.** `Image.save(..., "HEIF")` crashes the process via libheif's `_finish_add_image`; decoding (`Image.open`) works fine. `metascan/utils/heic.py` runs a subprocess decode probe (`_heif_decode_probe`) before `register_heif_opener()` so a broken native lib disables HEIC instead of taking down the scanner. Tests must NOT encode HEIF via Pillow — use the embedded `_HEIF_1X1_B64` fixture and write bytes to disk instead. The companion `_heif_encode_probe` exists for any test that genuinely needs encoding (currently none).
- **FAISS test vectors must use dim >= 32** to avoid SIMD alignment crashes on ARM (Apple Silicon). Tests normalize all vectors for IndexFlatIP.
- **`KMP_DUPLICATE_LIB_OK=TRUE`** is set in `tests/conftest.py` to prevent OpenMP duplicate library crash when torch + faiss-cpu both link libomp on macOS.
- **`httpx` / `httpcore` loggers are pinned to WARNING.** Set in
  `backend/main.py` at module load. `VlmClient`'s `/health` probe
  hits the server up to 10×/sec during model load (~30–60 s on CPU),
  and httpx's default INFO-per-request logging dumped hundreds of
  `503 Service Unavailable` lines per spawn. Don't relax this without
  also rate-limiting or quieting the probe.
- **Every log file goes through `metascan/utils/log_files.py`: 10 MB live
  file, the 3 most recent rollovers kept** (`LOG_MAX_BYTES` /
  `LOG_BACKUP_COUNT`, stdlib `RotatingFileHandler` underneath — 40 MB
  worst case per log). Never open a log with a bare `open(path, "a")` or
  build a `FileHandler` elsewhere; `tests/test_log_files.py` greps
  `metascan/` and `backend/` and fails on one. `logs/
  metadata_extraction_report.txt` was a bare append and reached **4.25 GB
  in one full import** — every successful extraction dumped its whole
  metadata dict, embedded workflow graph included (~170 KB per image
  pretty-printed). Rotation bounds the size, not the write volume, so
  success entries now summarise it: `MetadataParsingLogger._without_graph`
  replaces `raw_metadata` with `<omitted: prompt, workflow>` on a shallow
  copy (the caller's dict is what the scanner stores as
  `generation_data` — never mutate it). Failure entries still carry their
  truncated `raw_data` excerpt. `rotating_file_handler`
  is for ordinary log streams (`server.log`, `embedding_worker.log`,
  `~/.metascan/logs/upscaler.log`); `get_file_logger` is for report files
  written verbatim (the extraction report and its error CSV) and shares
  ONE handler per path — two handlers on one file rotate it out from under
  each other. `BoundedFileHandler` re-stamps a `header` after every
  rollover (the CSV must stay `DictReader`-parseable on its own) and
  reopens a file deleted underneath it, since logs get cleared by hand
  while the server runs. `RotatingFileHandler` is thread-safe but NOT
  process-safe: one file per process. The server's own `logs/server.log`
  is installed from the `lifespan`, not at import, so importing
  `backend.main` in a test creates nothing.
- **Lifespan shuts the event source down before its consumer.** The
  shutdown block in `backend/main.py`'s `lifespan` calls
  `comfy_client.shutdown()` **before** `storyboard_runner.aclose()`
  (each in its own try/except). `comfy_client.on_job_event` fans `job_outputs`
  out to both `ws_manager.broadcast_sync` and
  `storyboard_runner.handle_job_event`, and the latter schedules a
  fire-and-forget ingest task; closing the runner first would leave a
  window where a collect task completing between the two shutdowns spawns
  an ingest task nobody ever awaits.

## Documentation Layout

User-facing documentation is split between a thin `README.md` and per-topic files under `docs/` (one per topic, kebab-case; `ls docs` lists them).

**README.md is the index, not a kitchen sink.** It carries the overview, screenshots, release notes, Quick Start, and a Documentation section that links to every `docs/*.md` file. New top-level sections that grow past a screen or two should be moved into `docs/` and linked, not appended to README.

**`CLAUDE.md` plus the path-scoped files in `.claude/rules/` are the canonical rule set.** When `docs/developer-guidelines.md` would duplicate a project-rule list (commit conventions, project rules, common-task patterns), it links here instead — keep the rules in one place to avoid drift.

When adding new user-facing documentation:
1. Drop a new file under `docs/<topic>.md` (kebab-case, lowercase). Start with a `[← Back to README](../README.md)` link.
2. Add a one-line entry to README.md's **Documentation** section.
3. If the topic has codebase rules engineers must follow, also add them to `CLAUDE.md` (or the matching `.claude/rules/` file) and link from the docs page (don't duplicate).

## Common Tasks

### Adding a new API endpoint
1. Create route in `backend/api/<module>.py`.
2. If it needs DB access, add the sync DB method in `metascan/core/database_sqlite.py`, then an async wrapper in `backend/services/<domain>_service.py` via `asyncio.to_thread`. (Example split: `MediaService` for media reads; `FoldersService` for folder CRUD. Don't dump everything into `media_service.py`.)
3. Register router in `backend/main.py`.
4. Add a typed fetcher to `frontend/src/api/<domain>.ts`.
5. If mutations should sync across tabs, broadcast on a new or existing WS channel via `ws_manager.broadcast_sync(<channel>, <event>, payload)` from the handler and subscribe with `useWebSocket(<channel>, …)` on the frontend.

### Adding a tag axis / extending the CLIP vocabulary
1. Drop a new `<axis>.txt` under `data/vocabulary/` (one term per line, `#` comments).
2. Register the filename in `metascan/core/vocabulary.py` (`<AXIS>_FILENAME`, `_add_all(...)` call with the axis label).
3. The cache fingerprint hashes the source files — next worker run will re-encode automatically.
4. No DB migration needed; tags still flow through `indices(index_type='tag')` with source `'clip'`.

### Adding a live inference request type
1. Extend `inference_worker.py` with a new `_handle_<type>` method + dispatch in `run()`.
2. Add a matching `async <name>(...)` helper on `InferenceClient` that calls `_request(...)`.
3. Call it from `backend/api/similarity.py` (or a new router). Reuse `_ensure_worker_ready` to keep cold starts sane.
